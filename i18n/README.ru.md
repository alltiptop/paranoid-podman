# paranoid-podman

`paranoid-podman` — экспериментальная пользовательская обёртка для rootless
Podman и `podman-compose`. Она предназначена для разработчиков, которые иногда
запускают контейнерные команды из проектов, которым не полностью доверяют.

Проект добавляет простые и прямые ограничения против распространённых способов
выхода контейнера за ожидаемые границы и ошибок доступа к хосту, сохраняя обычные
сценарии локальной разработки. Это не антивирус, не корпоративный продукт безопасности
и не полноценная песочница.

> [!WARNING]
> Это эшелонированная защита, а не абсолютная гарантия. Она может не остановить
> zero-day эксплойты, неизвестные техники атак, уязвимости ядра или runtime, а
> также процесс, который уже получил доступ к вашей пользовательской учётной
> записи на хосте.

## О проекте

Поток выполнения команды:

```text
команда podman / compose -> парсер -> политика -> проверенный настоящий провайдер
```

Безопасные аргументы сохраняются. Опасный доступ к хосту отклоняется, добавляются
выбранные безопасные значения по умолчанию, а защищённые файлы проекта
монтируются только для чтения внутри новых контейнеров.

Дизайн намеренно прямолинеен:

- блокировать самые прямые пути повышения привилегий и доступа к хосту;
- сохранять обычную разработку, пока она остаётся в границах проекта;
- предпочитать явные и понятные ограничения монтирования сканерам содержимого;
- завершаться с отказом, если важная для безопасности форма команды неизвестна; и
- честно документировать оставшиеся границы защиты.

<a id="what-it-protects"></a>

## Что он защищает

| Входные данные или поведение | Действие |
| --- | --- |
| Привилегированный режим, пространства имён хоста или других контейнеров, дополнительные привилегии ядра, устройства, произвольные параметры безопасности | Запретить |
| Сокеты Podman/Docker и чувствительные служебные пути хоста | Запретить |
| Корень файловой системы, весь домашний каталог пользователя, широкие системные деревья или bind шире проекта | Запретить |
| Явно указанные отдельные обычные файлы и каталоги | Разрешить и канонизировать |
| Bind-опции, меняющие владельца или метки хоста, например `U`, `idmap` или небезопасная смена меток | Запретить |
| Публикация портов | Сохранить обычные TCP/UDP-пробросы, включая все интерфейсы и адреса локальной сети |
| Учётные данные из окружения, сокеты рабочего стола и сеанса, переменные маршрутизации провайдера | Удалить или запретить |
| Существующая защищённая конфигурация проекта под монтированием с правом записи | Добавить вложенные монтирования только для чтения |
| `start`, `exec` или активный Compose lifecycle старого либо чужого контейнера | Запретить до пересоздания текущей установкой и политикой |
| Конфигурация Compose | Разобрать, проверить, переписать и выполнить приватный проверенный снимок |
| Очевидные явно записанные секреты в Compose или присваиваниях Dockerfile | Отклонить, не показывая значения |
| Учётные данные в корне контекста сборки, не исключённые ignore-файлом | Запретить до запуска сборки |

Прямые команды `run` и `create` также получают совместимые значения по умолчанию:
`no-new-privileges`, ограничение PID, отключённую автоматическую передачу proxy,
непостоянную restart policy и запрет неявного скачивания образа. Неизвестные
runtime-опции не передаются дальше.

### Защищённая конфигурация проекта

Обнаруженные пути со следующими именами доступны только для чтения внутри новых
контейнеров:

- `.devcontainer`, `.devcontainer.json`, `devcontainer.json`;
- `.dockerignore`, `.containerignore`;
- рабочие dotenv-файлы и распространённые конфигурационные файлы учётных данных; и
- `.git`, `.gitmodules`, `.git-credentials`.

Отсутствующие пути не создаются. Содержимое devcontainer не сканируется и не
переписывается: защита реализована правилами монтирования файловой системы. Для
Dockerfile выполняется только небольшая проверка явно записанных секретов, описанная ниже.

Dockerfile, Containerfile и Compose-файлы вне `.devcontainer` можно редактировать
внутри контейнера. Всё содержимое `.devcontainer` остаётся read-only. Для применения
новых прав монтирования существующие контейнеры нужно пересоздать.

Недоступные для чтения каталоги другого UID, например данные rootless-базы,
монтируются без обхода содержимого и изменения прав. Файлы внутри них не
покрываются автоматической защитой от записи.

По умолчанию `.git` доступен только для чтения. Для одного запуска его можно
оставить доступной для записи, не ослабляя остальные защищённые пути:

```bash
PODMAN_GUARD_PROTECT_GIT=0 podman compose up
```

### Проверка Compose

Адаптер Compose:

1. предварительно проверяет исходные файлы и получает конфигурацию с подставленными значениями;
2. проверяет доступ к хосту, пространства имён, монтирования, ресурсы и поддерживаемые поля;
3. записывает приватный снимок с правами `0600` и подставленными значениями;
4. запускает только этот проверенный снимок.

Монтирования внутри проекта проходят тихо. Перед `up` или `run` доступ к файлу или
каталогу хоста вне проекта требует подтверждения: оранжевый `[warning]` показывает
полный путь, сервис, режим доступа и исходный Compose-файл с номером строки.
Введите ровно `y` и Enter для этого запуска. Enter, другой ответ или EOF отменяет
операцию; без интерактивного терминала она блокируется без чтения stdin. Выбор
не сохраняется. Просмотр, удаление и команды для существующих контейнеров не
запрашивают подтверждения. Запрещённые пути и сокеты разрешить таким способом нельзя.

`PODMAN_GUARD_DEBUG=1` включает сводку без значений. Политика одинакова для терминала и
автоматизации. Отказы выделяются заголовком `BLOCKED`, `UNSUPPORTED` или `ERROR`, с
причиной и именем затронутого сервиса, если оно известно.

Диагностика Compose скрывает значения переменных окружения и исходные ошибки
провайдера. Проверка явно записанных секретов ограничена известными именами полей;
это не универсальный сканер.

Новые контейнеры Podman и Compose получают две метки происхождения: поколение
политики и случайный идентификатор установки. Запуск, возобновление и выполнение
кода требуют совпадения обеих меток. Одной заранее заданной метки политики в образе
недостаточно. Просмотр и удаление старых контейнеров остаются доступны.

Точные интерфейсы описаны в документах
[Direct Podman policy](../docs/direct-policy.md),
[Compose policy](../docs/compose-policy.md) и
[threat model](../docs/threat-model.md).

## Установка

Нужны Linux с rootless Podman 6.1.x, `podman-compose` 1.6.x, Python 3.10 или
новее с поддержкой виртуальных окружений и Bash. Для DevPod дополнительно нужны
DevPod и клиентские инструменты OpenSSH. Протестирована версия DevPod 0.6.15;
другие версии допускаются. Из репозитория, от обычного пользователя:

```bash
./install.sh install
```

Можно запустить `./install.sh` без аргументов: он покажет статус и меню —
`install` для новой установки или `update` / `uninstall` для существующей.
Enter завершает работу без изменений. Без интерактивного терминала выводятся
только статус и доступные действия; в скриптах указывайте команду явно.

`./install.sh --help` описывает параметры по командам. Параметры провайдеров
и wheel относятся к `install` / `update`; `--without-devpod` и
`--backup-existing` — только к `install`, `--devpod-ssh-config` — только
к `uninstall`. Для обычной установки дополнительные параметры не нужны.

Установщик сам находит Podman, Compose и DevPod, если он есть, скачивает
инструменты Python и зависимости, собирает приложение и устанавливает его в
отдельное окружение. Готовить пакеты, контрольные суммы и окружения самостоятельно
не нужно. Существующие команды сохраняются в резервной копии после подтверждения
и восстанавливаются при удалении.

Предварительный просмотр без скачивания и изменения файлов:

```bash
./install.sh install --dry-run
```

### Пути команд

Каталог команд по умолчанию — `${XDG_BIN_HOME:-$HOME/.local/bin}`.
Поставьте его первым в `PATH`, чтобы использовать защищённые команды:

```bash
export PATH="${XDG_BIN_HOME:-$HOME/.local/bin}:$PATH"
command -v podman docker compose-guard
```

Если каталог ещё не стоит первым, добавьте строку `export` в настройки оболочки.
Приложение хранится в `${XDG_DATA_HOME:-$HOME/.local/share}/paranoid-podman`.

### Обновление и удаление

Запускайте из репозитория с нужной версией приложения:

```bash
./install.sh update
./install.sh status
```

Удаление и восстановление сохранённых команд:

```bash
./install.sh uninstall
```

Для проверки статуса и меню `uninstall` / `Exit` запустите `./uninstall.sh`.
Enter завершает работу без изменений; без интерактивного терминала скрипт только
показывает информацию. `./uninstall.sh --help` описывает параметры удаления,
а `./uninstall.sh --dry-run` позволяет предварительно посмотреть действия после выбора в меню.

`--dry-run` также работает для обновления и удаления. Изменённые файлы установки не удаляются: установщик сообщает о них.
Чтобы добавить DevPod в установку без него, удалите приложение и установите заново
после установки DevPod. Затем потребуется пересоздать защищённые контейнеры.

### Необязательные настройки

`--without-devpod` оставляет только защиту Podman и Compose. `--devpod PATH`
задаёт исполняемый файл вне `PATH`; `--podman` и `--compose-provider` заменяют
автоматический поиск. `--backup-existing` разрешает резервное копирование без
интерактивного подтверждения. Для других каталогов используйте согласованные
`--bindir` и `--libdir`.

SSH-конфигурации в стандартном каталоге DevPod восстанавливаются автоматически.
Для контекстов в другом `DEVPOD_HOME` явно передайте каждый нестандартный путь:

```bash
./install.sh uninstall --devpod-ssh-config /absolute/path/to/ssh-config
```

[Дополнительная инструкция по установке без сети](../docs/wheel-packaging.md)
описывает подготовленные пакеты. Обычная установка не требует этих параметров.

## Использование

Запускайте команды из существующего каталога проекта. Замените
`localhost/my-dev-image:latest` образом, который уже есть локально: прямой запуск
использует `--pull=never`. Для команд Compose нужны файл Compose и сервис `app`.

```bash
podman run --rm -v .:/workspace localhost/my-dev-image:latest
podman compose up
podman compose ps
podman compose exec app sh
podman compose run --rm --build app
podman compose down
```

Разовые задачи Compose поддерживают профили, `--no-deps`, параметры окружения,
пользователя, рабочего каталога и портов. `run --build` останавливается при ошибке
сборки. Поддерживаются `up --force-recreate` и явный сброс `down --volumes
--remove-orphans`; последний удаляет тома проекта.

Для совместимых сценариев устанавливаются команды-псевдонимы `docker`, `podman-compose` и
`docker-compose`. Команды за пределами проверенного интерфейса запрещены; для
администрирования хоста осознанно вызывайте настоящий бинарный файл Podman.

Отказы политики прямого Podman и Compose завершаются кодом 125 и показывают
причину и строку `next step:` без секретных значений.
Ошибка контекста сборки сразу перечисляет все найденные
пути. Исключите действующие dotenv-файлы и распространённые файлы учётных данных
из копируемых файлов сборки через `.containerignore` или `.dockerignore`. `.git`
разрешена в контексте сборки и остаётся доступной в рабочем пространстве, где обёртка
по умолчанию защищает её отдельным монтированием только для чтения.

Прямой защищённый запуск использует `--pull=never`, поэтому образ должен уже
существовать. Для скачивания и сборки образов
в DevPod предусмотрены только проверенные формы команд.

Для проверки и исправления исключений контекста сборки:

```bash
paranoid-podman build-context audit .
paranoid-podman build-context protect .
```

`protect` предлагает выбрать пути; `--all` применяет все найденные исключения без
запроса. Команда меняет только стандартный ignore-файл и не обходит политику.

## DevPod

Новые контейнеры DevPod получают hostname по имени workspace. Явно заданный hostname
сохраняется; при сокращении или нормализации имени добавляется короткий хеш. Для уже
созданных контейнеров требуется пересоздание.

Обёртка обрабатывает проверенные формы команд Docker- и Compose-драйверов
DevPod 0.6.15, включая:

- обнаружение, inspect, start, stop, logs, exec и удаление контейнера;
- inspect, pull, build, tag и push образа;
- приватный поток копирования для настройки `/etc/passwd` и `/etc/group`;
- поиск Compose-проекта, project names, project `.env` и сгенерированные
  override-файлы; и
- Compose build, up, stop и down.

DevPod соблюдает общую политику создания контейнеров. Привилегированный режим,
пространства имён хоста, сокеты контейнерного движка, опасные привилегии ядра и
слишком широкие монтирования с хоста будут отклонены.

Защита вложенных путей от записи и метки происхождения применяются при создании
контейнера. Старое рабочее пространство DevPod нужно пересоздать, прежде чем
запускать его через обёртку. То же относится к полной переустановке, которая
создаёт новый идентификатор установки. Команды удаления остаются доступны.
Чтобы разрешить запись в `.git`, запускайте DevPod с `PODMAN_GUARD_PROTECT_GIT=0`.

### Изоляция SSH-учётных данных

IDE выбирает DevPod: используются его стандартные настройки, настройки
рабочего пространства или параметр `--ide`. Обёртка не требует конкретного редактора.
Открытие и повторное подключение в режиме IDE-only вручную проверены на Codium;
другие IDE и полный сценарий Compose-драйвера ещё требуют проверки.
Ошибка времени жизни сокета проектного агента обнаружена в сочетании Codium и
Open Remote - SSH 0.1.2: [DEV-001](../KNOWN_ISSUES.md#dev-001-vscode-loses-the-project-ssh-agent-socket).
Обычные подключения OpenSSH и `devpod ssh` проверены с одним проектным ключом.

В интерактивном меню: **1** — создать проектный ключ, **2** — IDE без учётных данных
хоста, **3** — выбрать существующий проектный ключ, **4** — полный агент хоста на один
запуск с точным подтверждением `y`, **5** — отмена. Enter выбирает пункт 1;
для режима IDE-only явно выберите **2**.

Проектный режим запускает отдельный `ssh-agent` ровно с одним проверенным
ключом. Закрытый ключ не копируется и не монтируется в контейнер, но код внутри
может просить агента подписывать данные этим ключом. Ограничьте публичный ключ
одним репозиторием на GitHub, GitLab или Gitea.

Защищённые режимы отключают автоматическую передачу учётных данных Git и реестра
образов, агента GPG и ключа подписи SSH в выбранном контексте DevPod. Отдельный
`devpod build` без настроенного режима не запрашивает выбор и не передаёт учётные
данные хоста в рабочее пространство.

Чтобы DevPod не открыл IDE до защиты SSH-блока, обёртка сначала создаёт
рабочее пространство с `--open-ide=false`, ограничивает блок, а затем открывает IDE без
повторного создания контейнера и без новой записи SSH-конфига.

Существующий закрытый ключ должен быть выделен только для проекта и не должен
лежать непосредственно в `~/.ssh`; подкаталог допустим.

```bash
paranoid-podman devpod audit WORKSPACE
paranoid-podman devpod configure WORKSPACE
paranoid-podman devpod key show WORKSPACE
paranoid-podman devpod key stop WORKSPACE
```

Состояние определяется по SSH-блоку DevPod и ключам в
`~/.ssh/paranoid-podman/`; отдельный файл политики не создаётся. Подробности:
[изоляция учётных данных DevPod](../docs/devpod-credentials.md) (английский).

Замените `WORKSPACE` существующим идентификатором рабочего пространства.
При необходимости указывайте соответствующие `--context`, `--devpod-home` и
`--ssh-config`. Для нового локального проекта передайте `devpod up` существующий
каталог: несуществующий путь может быть принят за URL репозитория.
Выбирайте IDE-only при первом интерактивном `up`; до создания SSH-блока DevPod
команда `configure` не может сохранить этот режим. См.
[пример локального проекта](../docs/devpod-credentials.md#open-a-local-workspace).

Защищённые режимы также отключают автоматический поиск закрытых ключей.
Настройки контекста действуют на все его рабочие пространства.

## Совместимость

| Компонент | Совместимость |
| --- | --- |
| Операционная система | Linux |
| Python | 3.10 и новее |
| Podman | Rootless 6.1.x |
| Провайдер Compose | `podman-compose` 1.6.x через `podman compose` |
| DevPod | Протестирована 0.6.15; другие версии допускаются; проверенные команды Docker/Compose и ограничения IDE описаны выше |
| Docker Compose v2 | Не поддерживается |

Установщик отклоняет непроверенные основные и дополнительные серии версий Podman
и Compose. Обёртки зависят от поведения команд этих программ, поэтому каждая новая
серия требует проверки совместимости.

Совместимость других версий DevPod пока не проверена. Проверки доступа к
учётным данным и допустимости команд продолжают действовать.

<a id="limitations"></a>

## Ограничения

- Проверка ignore-файлов требует полного исключения чувствительных путей в корне.
  Повторное включение вложенных файлов или неподдерживаемые шаблоны могут
  потребовать явного исключения последним правилом. Для дополнительных контекстов
  образов нужен явный префикс транспорта. См. [ограничения сборки](../docs/direct-policy.md#build-boundary).
- Агент может подписывать данные проектным ключом, даже не раскрывая закрытый
  ключ. Ограничения доступа к репозиторию должны быть заданы на Git-сервере.
- Обёртка в `PATH` не изолирует процессы хоста. Процесс от вашего пользователя
  может вызвать настоящий Podman или напрямую прочитать те же файлы.
- Защита не устраняет уязвимости ядра, Podman, среды исполнения OCI, образа и
  парсера, включая ещё неизвестные уязвимости.
- Обычная сеть контейнера не ограничивает исходящие соединения.
- Сборка может выполнять произвольные инструкции образа и читать любой файл
  контекста, не исключённый `.containerignore` или `.dockerignore`. Проверяются
  только распространённые пути учётных данных в корне и очевидные присваивания секретов.
- Старые и уже работающие контейнеры не получают новые ограничения монтирования.
  Команды запуска и выполнения отклоняют контейнеры без актуальных меток политики
  и установки.
- Метки происхождения — локальные признаки совместимости, а не криптографические
  подписи. Процесс от пользователя хоста может прочитать, скопировать или обойти их.
  Прямой запуск из исходников без идентификатора установки использует фиксированное
  значение для разработки. Установщик создаёт отдельный идентификатор каждой установки.
- Файлы могут измениться между проверкой и запуском провайдера.
- Поддерживается только часть команд и параметров Podman и Compose.

Для более сильной изоляции используйте временную виртуальную машину или отдельную
учётную запись с минимальными привилегиями.

<a id="development"></a>

## Разработка

Быстрые локальные проверки:

```bash
scripts/test.sh
scripts/check.sh syntax
```

Локальные тесты используют имитации провайдеров и временные каталоги home/config; унаследованные флаги интеграционных проверок отключаются. `scripts/check.sh` по умолчанию выбирает `local`: Ruff, mypy, Bandit, ShellCheck, офлайн `zizmor` и проверку исходников Gitleaks со скрытыми значениями секретов. `scripts/audit.sh dependencies` явно запускает сетевой аудит; `scripts/check.sh all` добавляет его, но не запускает реальные интеграции.

`scripts/format.sh` применяет форматирование. Инструменты устанавливаются отдельно по [CONTRIBUTING.md](../CONTRIBUTING.md). CI разделяет тесты, статические проверки, поиск секретов и аудит зависимостей.

Реализация находится в `src/paranoid_podman`. См. [карту кода](../docs/architecture.md) и [инструкции по сборке и офлайн-установке wheel](../docs/wheel-packaging.md).

| Каталог | Назначение |
| --- | --- |
| `src/paranoid_podman/` | Код приложения |
| `bin/` | Небольшие команды запуска из исходников и для тестов |
| `dist/` | Сгенерированные wheel и контрольная сумма |

Установщик отдельно создаёт команды в `--bindir`; они запускают приложение из
его собственного окружения Python. `bin/` остаётся частью исходников.

`scripts/test.sh compose-provider` явно выбирает проверку с реальным провайдером Compose. Она может обращаться к Podman, но не запускает контейнеры; используйте одноразовое окружение с проверенными версиями.
Этот набор также проверяет обычные сценарии через настоящий Compose и записывающую
заглушку движка; он добавлен в CI.

Дополнительные тесты с реальными контейнерами требуют локальный образ с `sh` и
`sleep`. Они не скачивают образ и используют только временные контейнеры с
уникальными именами:

```bash
PARANOID_PODMAN_TEST_IMAGE=docker.io/library/alpine:latest \
  scripts/test.sh rootless
```

Запускайте его только с проверенными версиями Podman и Compose в одноразовой
rootless-учётной записи без ценных контейнеров или учётных данных.

Отдельный тест SSH-агента создаёт временный ключ и сокет и не читает ваши обычные
SSH-ключи:

```bash
scripts/test.sh ssh-agent
```
