# paranoid-podman

`paranoid-podman` — експериментальна користувацька обгортка для rootless Podman
і `podman-compose`. Вона призначена для розробників, які іноді запускають
контейнерні команди з проєктів, яким не довіряють повністю.

Проєкт додає прості й прямі обмеження проти поширених способів виходу контейнера
за очікувані межі та помилок доступу до хоста, зберігаючи звичайні сценарії
локальної розробки. Це не антивірус, не корпоративний продукт безпеки і не
повноцінна пісочниця.

> [!WARNING]
> Це багаторівневий захист, а не абсолютна гарантія. Він може не зупинити
> zero-day експлойти, невідомі техніки атак, уразливості ядра чи runtime або
> процес, який уже має доступ до вашого користувацького облікового запису на хості.

## Про проєкт

Потік виконання команди:

```text
команда podman / compose -> парсер -> політика -> перевірений справжній провайдер
```

Безпечні аргументи зберігаються. Небезпечний доступ до хоста відхиляється,
додаються вибрані безпечні типові значення, а захищені файли проєкту монтуються
лише для читання всередині нових контейнерів.

Дизайн навмисно прямолінійний:

- блокувати найпряміші шляхи отримання привілеїв і доступу до хоста;
- зберігати звичайну розробку, поки вона лишається в межах проєкту;
- надавати перевагу явним і зрозумілим mount-обмеженням замість сканерів вмісту;
- завершуватися відмовою, коли важлива для безпеки форма команди невідома; та
- чесно документувати решту меж захисту.

<a id="what-it-protects"></a>

## Що він захищає

| Вхідні дані або поведінка | Дія |
| --- | --- |
| Привілейований режим, простори імен хоста чи інших контейнерів, додаткові привілеї ядра, пристрої або довільні параметри безпеки | Заборонити |
| Сокети Podman/Docker і чутливі службові шляхи хоста | Заборонити |
| Корінь файлової системи, весь домашній каталог, широкі системні дерева або bind ширший за проєкт | Заборонити |
| Явно вказані окремі звичайні файли та каталоги | Дозволити й канонікалізувати |
| Bind-опції, що змінюють власника чи мітки хоста, як-от `U`, `idmap` або небезпечна зміна міток | Заборонити |
| Опубліковані порти | Зберегти звичайні TCP/UDP-проброси, зокрема на всіх інтерфейсах і адресах локальної мережі |
| Облікові дані з оточення, сокети робочого столу й сеансу, змінні маршрутизації провайдера | Видалити або заборонити |
| Наявна захищена конфігурація проєкту під монтуванням із правом запису | Додати вкладені монтування лише для читання |
| `start`, `exec` або активний Compose lifecycle старого чи чужого контейнера | Заборонити до повторного створення поточною інсталяцією та політикою |
| Конфігурація Compose | Розгорнути, перевірити, переписати й виконати приватний перевірений знімок |
| Очевидні явно записані секрети у Compose або присвоєннях Dockerfile | Відхилити, приховавши значення |
| Облікові дані в корені контексту збирання, не виключені ignore-файлом | Заборонити до запуску збирання |

Прямі команди `run` і `create` також отримують сумісні типові значення:
`no-new-privileges`, обмеження PID, вимкнене автоматичне передавання proxy,
непостійну restart policy та відсутність неявного image pull. Невідомі
runtime-опції не передаються далі.

### Захищена конфігурація проєкту

Знайдені шляхи з такими іменами доступні лише для читання в нових контейнерах:

- `.devcontainer`, `.devcontainer.json`, `devcontainer.json`;
- `.dockerignore`, `.containerignore`;
- активні dotenv-файли та поширені конфігураційні файли облікових даних; і
- `.git`, `.gitmodules`, `.git-credentials`.

Відсутні шляхи не створюються. Вміст devcontainer не сканується й не
переписується: цей захист є правилом монтування файлової системи. Для Dockerfile
виконується лише невелика перевірка явно записаних секретів, описана нижче.

Dockerfile, Containerfile і Compose-файли поза `.devcontainer` можна редагувати
всередині контейнера. Увесь вміст `.devcontainer` залишається лише для читання.
Для застосування нових прав монтування наявні контейнери потрібно створити заново.

Недоступні для читання каталоги іншого UID, наприклад дані rootless-бази,
монтуються без обходу вмісту та зміни прав. Файли всередині них не
охоплюються автоматичним захистом від запису.

Типово `.git` доступний лише для читання. Для одного запуску його можна лишити
writable, не послаблюючи інші захищені шляхи:

```bash
PODMAN_GUARD_PROTECT_GIT=0 podman compose up
```

### Перевірка Compose

Адаптер Compose:

1. попередньо перевіряє початкові файли та отримує конфігурацію з підставленими значеннями;
2. перевіряє доступ до хоста, простори імен, монтування, ресурси й підтримувані поля;
3. записує приватний знімок із правами `0600` та підставленими значеннями;
4. запускає лише цей перевірений знімок.

Монтування всередині проєкту проходять тихо. Перед `up` або `run` доступ до файлу чи
каталогу хоста поза проєктом потребує підтвердження: помаранчевий `[warning]` показує
повний шлях, сервіс, режим доступу та початковий Compose-файл із номером рядка.
Введіть саме `y` і Enter для цього запуску. Enter, інша відповідь або EOF скасовує
операцію; без інтерактивного термінала вона блокується без читання stdin. Вибір
не зберігається. Перегляд, видалення й команди для наявних контейнерів не потребують
підтвердження. Заборонені шляхи та сокети так дозволити не можна.

`PODMAN_GUARD_DEBUG=1` вмикає підсумок без значень. Політика однакова для термінала й
автоматизації. Відмови виділяються заголовком `BLOCKED`, `UNSUPPORTED` або `ERROR`, із
причиною та назвою відповідного сервісу, якщо вона відома.

Діагностика Compose приховує значення змінних середовища та початкові помилки
провайдера. Перевірка явно записаних секретів обмежена відомими іменами полів;
це не універсальний сканер.

Нові контейнери Podman і Compose отримують дві мітки походження: покоління політики
та випадковий ідентифікатор встановлення. Запуск, відновлення та виконання коду
потребують збігу обох міток. Однієї заздалегідь заданої мітки політики в образі
недостатньо. Перегляд і видалення старих контейнерів залишаються доступними.

Точні інтерфейси описано в документах
[Direct Podman policy](../docs/direct-policy.md),
[Compose policy](../docs/compose-policy.md) і
[threat model](../docs/threat-model.md).

## Встановлення

Потрібні Linux із rootless Podman 6.1.x, `podman-compose` 1.6.x, Python 3.10 або
новіший із підтримкою віртуальних середовищ і Bash. Для DevPod також потрібні
DevPod та клієнтські інструменти OpenSSH. Протестовано DevPod 0.6.15;
інші версії дозволені. З репозиторію, від звичайного користувача:

```bash
./install.sh install
```

Можна запустити `./install.sh` без аргументів: він покаже стан і меню —
`install` для нового встановлення або `update` / `uninstall` для наявного.
Enter завершує роботу без змін. Без інтерактивного термінала показуються лише
стан і доступні дії; у скриптах указуйте команду явно.

`./install.sh --help` описує параметри за командами. Параметри провайдерів
і wheel стосуються `install` / `update`; `--without-devpod` і
`--backup-existing` — лише `install`, а `--devpod-ssh-config` — лише
`uninstall`. Для звичайного встановлення додаткові параметри не потрібні.

Інсталятор сам знаходить Podman, Compose і DevPod, якщо він є, завантажує
інструменти Python і залежності, збирає застосунок та встановлює його в окреме
середовище. Готувати пакети, контрольні суми й середовища самостійно не потрібно.
Наявні команди зберігаються в резервних копіях після підтвердження та відновлюються
під час видалення.

Попередній перегляд без завантажень і змін файлів:

```bash
./install.sh install --dry-run
```

### Шляхи команд

Типовий каталог команд — `${XDG_BIN_HOME:-$HOME/.local/bin}`.
Поставте його першим у `PATH`, щоб використовувати захищені команди:

```bash
export PATH="${XDG_BIN_HOME:-$HOME/.local/bin}:$PATH"
command -v podman docker compose-guard
```

Якщо каталог ще не стоїть першим, додайте рядок `export` до налаштувань оболонки.
Застосунок зберігається в `${XDG_DATA_HOME:-$HOME/.local/share}/paranoid-podman`.

### Оновлення та видалення

Запускайте з репозиторію з потрібною версією застосунку:

```bash
./install.sh update
./install.sh status
```

Видалення та відновлення збережених команд:

```bash
./install.sh uninstall
```

Для перевірки стану й меню `uninstall` / `Exit` запустіть `./uninstall.sh`.
Enter завершує роботу без змін; без інтерактивного термінала скрипт лише показує
інформацію. `./uninstall.sh --help` описує параметри видалення, а
`./uninstall.sh --dry-run` показує заплановані дії після вибору в меню.

`--dry-run` також працює для оновлення та видалення. Змінені файли встановлення не видаляються: інсталятор повідомляє про них.
Щоб додати DevPod до встановлення без нього, видаліть застосунок і встановіть знову
після встановлення DevPod. Захищені контейнери після цього треба створити заново.

### Необов’язкові налаштування

`--without-devpod` залишає лише захист Podman і Compose. `--devpod PATH` задає
виконуваний файл поза `PATH`; `--podman` і `--compose-provider` замінюють автоматичний
пошук. `--backup-existing` дозволяє резервне копіювання без інтерактивного
підтвердження. Для інших каталогів узгоджено використовуйте `--bindir` і `--libdir`.

SSH-конфігурації в типовому каталозі DevPod відновлюються автоматично.
Для контекстів в іншому `DEVPOD_HOME` явно передайте кожен нестандартний шлях:

```bash
./install.sh uninstall --devpod-ssh-config /absolute/path/to/ssh-config
```

[Додаткова інструкція встановлення без мережі](../docs/wheel-packaging.md)
описує підготовлені пакети. Звичайне встановлення не потребує цих параметрів.

<a id="usage"></a>

## Використання

Запускайте команди з наявного каталогу проєкту. Замініть
`localhost/my-dev-image:latest` образом, що вже є локально: прямий запуск
використовує `--pull=never`. Compose потребує файлу конфігурації та сервісу `app`.

```bash
podman run --rm -v .:/workspace localhost/my-dev-image:latest
podman compose up
podman compose ps
podman compose exec app sh
podman compose run --rm --build app
podman compose down
```

Разові завдання Compose підтримують профілі, `--no-deps`, параметри середовища,
користувача, робочого каталогу та портів. `run --build` зупиняється при помилці збірки.
Підтримуються `up --force-recreate` та явне скидання `down --volumes --remove-orphans`;
останнє видаляє томи проєкту.

Для сумісних workflows встановлюються aliases `docker`, `podman-compose` і
`docker-compose`. Команди поза перевіреним інтерфейсом заборонені; для
адміністрування хоста свідомо викликайте справжній бінарний файл Podman.

Відмови політики прямого Podman і Compose завершуються кодом 125 і показують
причину та рядок `next step:` без секретних значень.
Помилка build context одразу перелічує всі виявлені
шляхи. Виключіть чинні dotenv-файли та поширені шляхи облікових даних із
копійованих build inputs через `.containerignore` або `.dockerignore`. `.git`
дозволена в build context і залишається доступною в runtime workspace, де guard
типово захищає її окремим read-only mount.

Прямий guarded run використовує `--pull=never`, тож образ має вже існувати.
DevPod має вузько перевірені форми image pull/build lifecycle.

Для перевірки й виправлення виключень контексту збирання:

```bash
paranoid-podman build-context audit .
paranoid-podman build-context protect .
```

`protect` пропонує вибір шляхів; `--all` застосовує всі виявлені виключення без
запиту. Команда змінює лише стандартний ignore-файл і не обходить політику.

<a id="devpod"></a>

## DevPod

Нові контейнери DevPod отримують hostname за назвою workspace. Явно заданий hostname
зберігається; під час скорочення або нормалізації додається короткий хеш. Наявні
контейнери потрібно створити заново.

Обгортка обробляє перевірені форми команд Docker- і Compose-драйверів
DevPod 0.6.15, зокрема:

- пошук, inspect, start, stop, logs, exec і видалення контейнера;
- inspect, pull, build, tag і push образу;
- приватний потік копіювання для налаштування `/etc/passwd` і `/etc/group`;
- пошук Compose-проєкту, project names, project `.env` і згенеровані
  override-файли; та
- Compose build, up, stop і down.

DevPod дотримується спільної політики створення контейнерів. Привілейований режим,
простори імен хоста, сокети контейнерного рушія, небезпечні привілеї ядра та
надто широкі монтування з хоста буде відхилено.

Захист вкладених шляхів від запису та мітки походження застосовуються під час
створення контейнера. Старе робоче середовище DevPod потрібно створити заново перед
запуском через обгортку. Це також стосується повного перевстановлення, яке створює
новий ідентифікатор встановлення. Команди видалення залишаються доступними.
Щоб дозволити запис у `.git`, запускайте DevPod із `PODMAN_GUARD_PROTECT_GIT=0`.

### Ізоляція SSH-облікових даних

IDE вибирає DevPod: використовуються його типові налаштування, налаштування
робочого середовища або параметр `--ide`. Обгортка не вимагає конкретного редактора.
Відкриття й повторне підключення в режимі IDE-only вручну перевірені на Codium;
інші IDE та повний сценарій Compose-драйвера ще потребують перевірки.
Помилку часу життя сокета проєктного агента виявлено в поєднанні Codium та
Open Remote - SSH 0.1.2: [DEV-001](../KNOWN_ISSUES.md#dev-001-vscode-loses-the-project-ssh-agent-socket).
Нові підключення OpenSSH і `devpod ssh` перевірені з одним проєктним ключем.

Інтерактивне меню: **1** — створити ключ проєкту, **2** — IDE без облікових даних
хоста, **3** — вибрати наявний ключ проєкту, **4** — повний агент хоста на один запуск
із точним підтвердженням `y`, **5** — скасувати. Enter вибирає пункт 1;
для IDE-only явно виберіть **2**.

Проєктний режим запускає окремий `ssh-agent` рівно з одним перевіреним ключем.
Закритий ключ не копіюється й не монтується в контейнер, але код робочого середовища може
просити агента підписувати дані цим ключем. Обмежте публічний ключ одним
репозиторієм у GitHub, GitLab або Gitea.

Захищені режими вимикають автоматичне передавання облікових даних Git і реєстру
образів, агента GPG та ключа підпису SSH у вибраному контексті DevPod. Окремий
`devpod build` без налаштованого режиму не запитує вибір і не передає облікові дані
хоста до робочого середовища.

Щоб DevPod не відкрив IDE до захисту SSH-блоку, обгортка спочатку створює
робоче середовище з `--open-ide=false`, обмежує блок, а потім відкриває IDE без
повторного створення контейнера й без нового запису SSH-конфігурації.

Наявний закритий ключ має бути виділений лише для проєкту й не повинен лежати
безпосередньо в `~/.ssh`; підкаталог дозволено.

```bash
paranoid-podman devpod audit WORKSPACE
paranoid-podman devpod configure WORKSPACE
paranoid-podman devpod key show WORKSPACE
paranoid-podman devpod key stop WORKSPACE
```

Стан визначається з SSH-блоку DevPod і ключів у
`~/.ssh/paranoid-podman/`; окремий файл політики не створюється. Докладніше:
[ізоляція облікових даних DevPod](../docs/devpod-credentials.md) (англійською).

Замініть `WORKSPACE` наявним ідентифікатором робочого середовища. За потреби
вказуйте відповідні `--context`, `--devpod-home` і `--ssh-config`. Для нового локального
проєкту передайте `devpod up` наявний каталог: неіснуючий шлях може бути сприйнятий
як URL репозиторію. Вибирайте IDE-only під час першого інтерактивного `up`:
`configure` не збереже вибір до створення SSH-блоку DevPod. Див.
[локальний приклад](../docs/devpod-credentials.md#open-a-local-workspace).

Захищені режими також вимикають автоматичний пошук закритих ключів.
Налаштування контексту діють на всі його робочі середовища.

<a id="compatibility"></a>

## Сумісність

| Компонент | Сумісність |
| --- | --- |
| Операційна система | Linux |
| Python | 3.10 і новіший |
| Podman | Rootless 6.1.x |
| Провайдер Compose | `podman-compose` 1.6.x через `podman compose` |
| DevPod | Протестовано 0.6.15; інші версії дозволені; перевірені команди Docker/Compose та обмеження IDE описано вище |
| Docker Compose v2 | Не підтримується |

Інсталятор відхиляє неперевірені основні й додаткові серії версій Podman і Compose.
Обгортки залежать від поведінки команд цих програм, тому кожна нова серія потребує
перевірки сумісності.

Сумісність інших версій DevPod поки не перевірена. Перевірки доступу до облікових
даних і допустимості команд продовжують діяти.

<a id="limitations"></a>

## Обмеження

- Перевірка ignore-файлів вимагає повного виключення чутливих шляхів у корені.
  Повторне включення вкладених файлів або непідтримувані шаблони можуть вимагати
  явного виключення останнім правилом. Додаткові контексти образів потребують
  явного префікса транспорту. Див. [обмеження збирання](../docs/direct-policy.md#build-boundary).
- Агент може підписувати дані ключем проєкту без розкриття закритого ключа.
  Обмеження доступу до репозиторію має встановлювати Git-сервер.
- Обгортка в `PATH` не ізолює процеси хоста. Процес від вашого користувача може
  викликати справжній Podman або напряму прочитати ті самі файли.
- Захист не усуває вразливості ядра, Podman, середовища виконання OCI, образу та
  парсера, зокрема ще невідомі вразливості.
- Звичайна мережа контейнера не обмежує вихідні з’єднання.
- Збирання може виконувати довільні інструкції образу й читати будь-який файл
  контексту, не виключений `.containerignore` або `.dockerignore`. Перевіряються
  лише поширені шляхи облікових даних у корені та очевидні присвоєння секретів.
- Старі та вже запущені контейнери не отримують нових обмежень монтування.
  Команди запуску та виконання відхиляють контейнери без актуальних міток політики
  й встановлення.
- Мітки походження — локальні ознаки сумісності, а не криптографічні підписи.
  Процес від користувача хоста може прочитати, скопіювати чи обійти їх. Прямий запуск
  із вихідного коду без ідентифікатора встановлення використовує фіксоване значення
  для розробки. Інсталятор створює окремий ідентифікатор кожного встановлення.
- Файли можуть змінитися між перевіркою та запуском провайдера.
- Підтримується лише частина команд і параметрів Podman та Compose.

Для сильнішої ізоляції використовуйте тимчасову віртуальну машину або окремий
обліковий запис із мінімальними привілеями.

<a id="development"></a>

## Розробка

Швидкі локальні перевірки:

```bash
scripts/test.sh
scripts/check.sh syntax
```

Локальні тести використовують імітації провайдерів і тимчасові каталоги home/config; успадковані прапорці інтеграційних перевірок вимикаються. `scripts/check.sh` типово обирає `local`: Ruff, mypy, Bandit, ShellCheck, офлайн `zizmor` і перевірку вихідного коду Gitleaks із прихованими значеннями секретів. `scripts/audit.sh dependencies` явно запускає мережевий аудит; `scripts/check.sh all` додає його, але не запускає реальні інтеграції.

`scripts/format.sh` застосовує форматування. Інструменти встановлюються окремо за [CONTRIBUTING.md](../CONTRIBUTING.md). CI розділяє тести, статичні перевірки, пошук секретів і аудит залежностей.

Реалізація міститься в `src/paranoid_podman`. Див. [карту коду](../docs/architecture.md) та [інструкції зі збирання та офлайн-встановлення wheel](../docs/wheel-packaging.md).

| Каталог | Призначення |
| --- | --- |
| `src/paranoid_podman/` | Код застосунку |
| `bin/` | Невеликі команди запуску з вихідних файлів і для тестів |
| `dist/` | Згенеровані wheel і контрольна сума |

Інсталятор окремо створює команди в `--bindir`; вони використовують власне
середовище Python. `bin/` залишається частиною вихідного коду.

`scripts/test.sh compose-provider` явно обирає перевірку зі справжнім провайдером Compose. Вона може звертатися до Podman, але не запускає контейнери; використовуйте одноразове середовище з перевіреними версіями.
Цей набір також перевіряє звичайні сценарії через справжній Compose та записувальну
заглушку рушія; його додано до CI.

Додаткові тести зі справжніми контейнерами потребують локального образу з `sh` і
`sleep`. Вони не завантажують образ і використовують лише тимчасові контейнери з
унікальними іменами:

```bash
PARANOID_PODMAN_TEST_IMAGE=docker.io/library/alpine:latest \
  scripts/test.sh rootless
```

Запускайте його лише з перевіреними версіями Podman і Compose в одноразовому
rootless-акаунті без цінних контейнерів або облікових даних.

Тест SSH-агента створює тимчасові ключ і сокет та не читає ваші звичайні SSH-ключі:

```bash
scripts/test.sh ssh-agent
```

[CONTRIBUTING.md](../CONTRIBUTING.md).
