# paranoid-podman

`paranoid-podman` هو غلاف تجريبي على مستوى المستخدم لـ Podman بنمط rootless
ولـ `podman-compose`. وهو مخصص للمطورين الذين يشغّلون أحياناً أوامر الحاويات من
مشاريع لا يثقون بها ثقة كاملة.

يضيف المشروع حواجز بسيطة ومباشرة ضد أخطاء الهروب الشائعة من الحاوية والوصول
إلى المضيف، مع الحفاظ على مسارات عمل التطوير المحلي المعتادة. وهو ليس برنامج
مكافحة فيروسات، ولا منتج أمن مؤسسياً، ولا sandbox كاملة.

> [!WARNING]
> هذه حماية متعددة الطبقات وليست حماية مطلقة. قد لا توقف ثغرات zero-day أو
> تقنيات الهجوم غير المعروفة أو ثغرات kernel أو runtime، كما لا تقيّد عملية
> حصلت بالفعل على صلاحيات حساب المستخدم في المضيف.

## حول المشروع

يمر الأمر عبر المسار التالي:

```text
podman / compose command -> parser -> policy -> verified real provider
```

تُحفظ الوسائط الآمنة، ويُرفض الوصول الخطير إلى المضيف، وتُضاف إعدادات التقوية
الافتراضية المختارة، وتُركّب ملفات المشروع المحمية للقراءة فقط داخل الحاويات
الجديدة.

التصميم مباشر عن قصد:

- حظر أكثر طرق الصلاحيات والوصول إلى المضيف مباشرة؛
- إبقاء التطوير المعتاد عاملاً ما دام داخل حدود المشروع؛
- تفضيل قيود mount الصريحة والمفهومة على ماسحات المحتوى؛
- الرفض الآمن عند مواجهة صيغة أمر مجهولة ومرتبطة بالأمان؛ و
- توثيق الحدود المتبقية بوضوح وصدق.

## ما الذي يحميه

| الإدخال أو السلوك | الإجراء |
| --- | --- |
| privileged mode أو host/joined namespaces أو capabilities مضافة أو أجهزة أو security options عشوائية | رفض |
| sockets لمحرك Podman/Docker ومسارات runtime الحساسة في المضيف | رفض |
| جذر نظام الملفات أو home المستخدم بالكامل أو أشجار النظام الواسعة أو bind أوسع من المشروع | رفض |
| ملفات ومجلدات عادية منفردة ومحددة صراحة | سماح مع canonicalization |
| خيارات bind التي تغيّر الملكية أو labels في المضيف مثل `U` أو `idmap` أو relabeling غير الآمن | رفض |
| المنافذ المنشورة | الحفاظ على تعيينات TCP/UDP المعتادة، بما فيها جميع الواجهات وعناوين الشبكة المحلية |
| credentials المحيطة ونقاط desktop/session ومتغيرات routing الخاصة بالـ provider | إزالة أو رفض |
| إعدادات المشروع المحمية الموجودة تحت bind قابل للكتابة | إضافة submounts للقراءة فقط |
| `start` أو `exec` أو lifecycle نشط لـ Compose على حاوية قديمة أو أجنبية | رفض حتى تعيد السياسة والتثبيت الحاليان إنشاءها |
| إعدادات Compose | تحليلها والتحقق منها وإعادة كتابتها ثم تشغيل نسخة خاصة مدقّقة |
| literal secrets واضحة في Compose أو تعيينات Dockerfile | رفض مع إخفاء القيم |
| credentials في جذر build context غير مستثناة بملف ignore | رفض قبل تشغيل builder |

تحصل أوامر `run` و`create` المباشرة أيضاً على قيم افتراضية متوافقة مثل
`no-new-privileges` وحد PID وتعطيل تمرير proxy التلقائي وسياسة restart غير دائمة
وعدم تنفيذ image pull ضمني. لا تُمرر خيارات runtime غير المعروفة.

### إعدادات المشروع المحمية

تكون المسارات المكتشفة ذات الأسماء التالية للقراءة فقط داخل الحاويات الجديدة:

- `.devcontainer`, `.devcontainer.json` و`devcontainer.json`؛
- `.dockerignore` و`.containerignore`؛
- ملفات dotenv الفعلية وملفات إعداد credentials الشائعة؛ و
- `.git` و`.gitmodules` و`.git-credentials`.

لا تُنشأ المسارات غير الموجودة. لا يُفحص محتوى devcontainer ولا يُعاد كتابته؛
فهذه الحماية قاعدة mount في نظام الملفات. تحصل ملفات Dockerfile فقط على فحص
literal secrets الصغير الموضح لاحقاً.

يمكن تعديل ملفات Dockerfile وContainerfile وCompose خارج `.devcontainer` من داخل
الحاوية. يبقى كل محتوى `.devcontainer` للقراءة فقط. أعد إنشاء الحاويات الموجودة
لتطبيق أذونات التركيب الجديدة.

تُركّب المجلدات غير القابلة للقراءة والمملوكة لـ UID آخر، مثل بيانات قواعد
البيانات rootless، دون فحص محتواها أو تغيير أذوناتها. لا تشمل الحماية
التلقائية من الكتابة الملفات الموجودة داخلها.

يكون `.git` للقراءة فقط افتراضياً. ويمكن إبقاؤه قابلاً للكتابة لاستدعاء واحد
من دون إضعاف المسارات المحمية الأخرى:

```bash
PODMAN_GUARD_PROTECT_GIT=0 podman compose up
```

### مراجعة Compose

يقوم محوّل Compose بما يلي:

1. يفحص ملفات المصدر مبدئياً ويولّد الإعدادات المحلولة؛
2. يتحقق من الوصول إلى المضيف وnamespaces وmounts والموارد والحقول المدعومة؛
3. يكتب snapshot خاصاً بوضع `0600` بعد إتمام interpolation;
4. يشغّل ذلك الـ snapshot المدقّق فقط.

تبقى عمليات التركيب داخل المشروع صامتة. قبل `up` أو `run`، يتطلب الوصول إلى ملف
أو مجلد على المضيف خارج المشروع تأكيداً: يعرض `[warning]` برتقالي المسار الكامل
والخدمة ووضع الوصول وملف Compose الأصلي مع رقم السطر. اكتب `y` بالضبط ثم Enter
للسماح بهذه التركيبات لهذا الأمر. يلغي Enter وحده أو أي جواب آخر أو EOF العملية؛
ومن دون إدخال طرفية تُحظر العملية دون قراءة stdin. لا يُحفظ الاختيار. لا تتطلب
أوامر الفحص والإزالة والعمل على الحاويات الموجودة تأكيداً. لا يمكن السماح بالمسارات
أو المقابس المحظورة بهذه الطريقة.

`PODMAN_GUARD_DEBUG=1` ملخصاً يخفي القيم الحساسة. تنطبق السياسة نفسها على الطرفية
والأتمتة. يظهر الرفض بعنوان بارز `BLOCKED` أو `UNSUPPORTED` أو `ERROR` مع السبب واسم
الخدمة المتأثرة إن كان معروفاً.

لا تعرض تشخيصات Compose قيم متغيرات البيئة بعد استبدالها ولا أخطاء المزوّد الخام.
فحص literal secrets صغير ومعتمد على الأسماء عن قصد، وليس ماسح secrets عاماً.

تحصل الحاويات المباشرة وحاويات Compose الجديدة على اثنين من provenance labels
المحجوزة: جيل السياسة ومعرّف عشوائي للتثبيت المحلي. تتطلب العمليات القادرة على
بدء الكود أو استئنافه أو تنفيذه تطابق القيمتين قبل استخدام حاوية موجودة. لذلك لا
يمكن لصورة اجتياز الفحص بمجرد إعلان policy label العامة. يظل inspection للقراءة
فقط وcleanup متاحين لتشخيص الحاويات القديمة وإزالتها بأمان.

توجد الواجهات الدقيقة في
[سياسة Podman المباشرة](../docs/direct-policy.md) و
[سياسة Compose](../docs/compose-policy.md) و
[نموذج التهديدات](../docs/threat-model.md).

## التثبيت

تحتاج إلى Linux مع Podman بنمط rootless 6.1.x و`podman-compose` 1.6.x، وPython
3.10 أو أحدث مع دعم البيئات الافتراضية، وBash. لاستخدام DevPod تحتاج أيضاً إلى
DevPod وأدوات عميل OpenSSH. اختُبرت نسخة DevPod 0.6.15؛ وتُقبل النسخ الأخرى.
من مجلد المستودع، بحساب المستخدم العادي:

```bash
./install.sh install
```

يمكن تشغيل `./install.sh` دون معاملات لعرض الحالة وقائمة الإجراءات:
`install` لتثبيت جديد، أو `update` / `uninstall` لتثبيت موجود. اضغط Enter
للخروج دون تغييرات. دون طرفية تفاعلية، تُعرض الحالة والإجراءات المتاحة فقط؛
في السكربتات، حدّد الإجراء صراحةً.

يشرح `./install.sh --help` الخيارات بحسب الإجراء. خيارات المزوّدين وملفات
wheel تخص `install` / `update`؛ أما `--without-devpod` و`--backup-existing`
فتخصان `install` فقط، و`--devpod-ssh-config` يخص `uninstall` فقط. لا يحتاج
التثبيت العادي إلى خيارات إضافية.

يجد المثبّت Podman وCompose وDevPod إن كان موجوداً، وينزّل أدوات Python
والاعتماديات، ويبني التطبيق ويثبّته في بيئة خاصة. لا تحتاج إلى إعداد حزم أو
قيم تحقق أو بيئات Python بنفسك. تُحفظ الأوامر الموجودة في نسخ احتياطية بعد
تأكيدك وتُستعاد عند إزالة التطبيق.

معاينة دون تنزيل أو تغيير ملفات:

```bash
./install.sh install --dry-run
```

### موقع الأوامر

مجلد الأوامر الافتراضي هو `${XDG_BIN_HOME:-$HOME/.local/bin}`.
ضعه في بداية `PATH` لاستخدام الأوامر المحمية:

```bash
export PATH="${XDG_BIN_HOME:-$HOME/.local/bin}:$PATH"
command -v podman docker compose-guard
```

إذا لم يكن المجلد في البداية، أضف سطر `export` إلى إعدادات الصدفة.
يوجد التطبيق في `${XDG_DATA_HOME:-$HOME/.local/share}/paranoid-podman`.

### التحديث أو الإزالة

شغّل من المستودع الذي يحتوي إصدار التطبيق المطلوب:

```bash
./install.sh update
./install.sh status
```

إزالة التطبيق واستعادة الأوامر المحفوظة:

```bash
./install.sh uninstall
```

شغّل `./uninstall.sh` للتحقق من الحالة وعرض قائمة `uninstall` / `Exit`.
يخرج Enter دون تغييرات؛ ودون طرفية تفاعلية تُعرض المعلومات فقط.
يشرح `./uninstall.sh --help` خيارات الإزالة، ويعرض
`./uninstall.sh --dry-run` معاينة للإجراءات بعد اختيار الإزالة من القائمة.

يعمل `--dry-run` أيضاً مع التحديث والإزالة.
يُبلّغ عن ملفات التثبيت المعدّلة بدلاً من حذفها. لإضافة DevPod إلى تثبيت لم يتضمنه،
أزل التطبيق وأعد تثبيته بعد توفر DevPod. يلزم حينها إعادة إنشاء الحاويات المحمية.

### إعدادات اختيارية

يثبّت `--without-devpod` حماية Podman وCompose فقط. يحدد `--devpod PATH` ملفاً
تنفيذياً خارج `PATH`؛ ويستبدل `--podman` و`--compose-provider` الاكتشاف التلقائي.
يسمح `--backup-existing` بالنسخ الاحتياطي دون تأكيد تفاعلي. للمجلدات المخصصة،
استخدم قيماً متطابقة لـ `--bindir` و`--libdir`.

تُستعاد إعدادات SSH في مجلد DevPod الافتراضي تلقائياً. للسياقات ضمن
`DEVPOD_HOME` آخر، حدّد كل مسار مخصص لإعداد SSH:

```bash
./install.sh uninstall --devpod-ssh-config /absolute/path/to/ssh-config
```

يصف [دليل التثبيت المتقدم دون اتصال](../docs/wheel-packaging.md) الحزم المجهزة
مسبقاً. لا يحتاج التثبيت العادي إلى تلك الخيارات.

## الاستخدام

شغّل الأوامر من مجلد مشروع موجود. استبدل `localhost/my-dev-image:latest` بصورة
متاحة محلياً؛ فالتشغيل المباشر يستخدم `--pull=never`. تتطلب أوامر Compose ملف إعداد
وخدمة باسم `app`.

```bash
podman run --rm -v .:/workspace localhost/my-dev-image:latest
podman compose up
podman compose ps
podman compose exec app sh
podman compose run --rm --build app
podman compose down
```

تدعم مهام Compose المؤقتة profiles و`--no-deps` وخيارات البيئة والمستخدم ومجلد العمل
والمنافذ. يتوقف `run --build` عند فشل البناء. يُدعم `up --force-recreate` وإعادة الضبط
الصريحة `down --volumes --remove-orphans`؛ والأخيرة تحذف وحدات تخزين المشروع.

تُثبّت الأسماء البديلة `docker` و`podman-compose` و`docker-compose` لمسارات العمل
المتوافقة. تُرفض الأوامر خارج الواجهة المدققة؛ استخدم ملف Podman الحقيقي عمداً
لإدارة المضيف.

تنتهي حالات رفض سياسة Podman المباشر وCompose بالرمز 125 وتعرض السبب وسطر
`next step:` من دون قيم سرية.
تسرد أخطاء build context جميع المسارات المكتشفة دفعة واحدة. استبعد ملفات dotenv
الفعلية ومسارات بيانات الاعتماد الشائعة من مدخلات build المنسوخة عبر
`.containerignore` أو `.dockerignore`. يُسمح بوجود `.git` في build context ويظل
متاحاً في runtime workspace، حيث يحميه guard افتراضياً عبر mount منفصل read-only.

تستخدم عمليات run المباشرة المحمية `--pull=never`، لذا يجب أن تكون الصورة
موجودة مسبقاً. لدى DevPod صيغ محدودة ومدققة لـ image pull/build lifecycle.

لفحص استثناءات سياق البناء وتصحيحها:

```bash
paranoid-podman build-context audit .
paranoid-podman build-context protect .
```

يتيح `protect` اختيار المسارات؛ ويطبّق `--all` جميع الاستثناءات المكتشفة دون سؤال.
لا يتغير إلا ملف ignore القياسي، ولا تُتجاوز السياسة.

## DevPod

تستخدم حاويات DevPod الجديدة اسم workspace بوصفه hostname. يبقى hostname المحدد صراحةً
كما هو؛ وتضاف لاحقة hash قصيرة عند اختصار الاسم أو تطبيعه. تحتاج الحاويات الموجودة إلى
إعادة الإنشاء لتطبيق التغيير.

يعالج الغلاف صيغ الأوامر المدققة لمشغّلي Docker وCompose في DevPod 0.6.15، ومنها:

- اكتشاف الحاوية وinspect وstart وstop وlogs وexec والإزالة؛
- inspect وpull وbuild وtag وpush للصورة؛
- مسار النسخ الخاص لإعداد `/etc/passwd` و`/etc/group`؛
- البحث عن مشروع Compose وأسماء المشروع وملف `.env` وملفات override المولدة؛ و
- عمليات Compose build وup وstop وdown.

لا يتجاوز DevPod سياسة الإنشاء العامة. تظل مساحة العمل التي تطلب privileged
mode أو host namespaces أو engine sockets أو capabilities خطرة أو host mount
واسع مرفوضة.

تُطبق read-only submounts وprovenance labels عند إنشاء الحاوية. بعد تثبيت هذه
الآلية، أعد إنشاء DevPod workspace قديمة قبل تشغيلها أو الدخول إليها عبر الغلاف.
وينطبق ذلك أيضاً بعد إعادة تثبيت كاملة، لأنها تحصل على معرّف تثبيت جديد. تظل
أوامر cleanup متاحة. لإبقاء `.git` قابلاً للكتابة، شغّل DevPod مع
`PODMAN_GUARD_PROTECT_GIT=0`.

### عزل بيانات اعتماد SSH

يختار DevPod بيئة التطوير IDE وفق إعداداته الافتراضية أو إعدادات مساحة العمل أو
الخيار `--ide`؛ ولا يفرض الغلاف محرراً معيناً. جرى التحقق يدوياً من الفتح وإعادة
الاتصال بوضع IDE-only باستخدام Codium. ما زالت البيئات الأخرى ومساحة العمل الكاملة
بمشغّل Compose تحتاج إلى اختبارات قبول. لوحظ خلل في عمر مقبس وكيل المشروع عند
الجمع بين Codium وOpen Remote - SSH 0.1.2:
[DEV-001](../KNOWN_ISSUES.md#dev-001-vscode-loses-the-project-ssh-agent-socket).
وجرى التحقق من اتصالات OpenSSH و`devpod ssh` الجديدة بمفتاح مشروع واحد.

القائمة التفاعلية: **1** إنشاء مفتاح مشروع، **2** وصول IDE دون بيانات اعتماد المضيف،
**3** اختيار مفتاح مشروع موجود، **4** إتاحة وكيل المضيف الكامل مرة واحدة بعد إدخال
`y` بالضبط، **5** إلغاء. يختار Enter الخيار 1؛ اختر **2** صراحة لوضع IDE-only.

يشغّل وضع المشروع `ssh-agent` مخصصًا به هوية واحدة متحقق منها. لا يُنسخ المفتاح
الخاص ولا يُركّب داخل الحاوية، لكن يمكن لكود مساحة العمل أن يطلب من الوكيل
التوقيع به. قيّد المفتاح العام بمستودع واحد في GitHub أو GitLab أو Gitea.

تعطّل الأوضاع المحمية الحقن التلقائي لبيانات اعتماد Git وregistry وGPG-agent
ومفتاح توقيع SSH في سياق DevPod المحدد. لا يطلب `devpod build` المستقل بلا وضع
مهيأ اختيارًا تفاعليًا ولا يمرر بيانات اعتماد المضيف إلى workspace.

لمنع DevPod من فتح IDE قبل حماية كتلة SSH، ينشئ الغلاف مساحة العمل أولاً مع
`--open-ide=false`، ثم يقيّد الكتلة ويفتح IDE من دون إعادة إنشاء الحاوية أو
إعادة كتابة إعداد SSH.

يجب أن يكون المفتاح الخاص الموجود مخصصاً للمشروع فقط، وألا يكون مباشرة داخل
`~/.ssh`؛ ويمكن وضعه في مجلد فرعي.

```bash
paranoid-podman devpod audit WORKSPACE
paranoid-podman devpod configure WORKSPACE
paranoid-podman devpod key show WORKSPACE
paranoid-podman devpod key stop WORKSPACE
```

تُستنتج الحالة من كتلة SSH التي يديرها DevPod ومن المفاتيح تحت
`~/.ssh/paranoid-podman/`، ولا يُنشأ ملف سياسة منفصل. راجع
[عزل بيانات اعتماد DevPod](../docs/devpod-credentials.md) (بالإنجليزية).

استبدل `WORKSPACE` بمعرّف مساحة عمل موجودة. استخدم قيماً متطابقة لـ `--context`
و`--devpod-home` و`--ssh-config` عند الحاجة. للمشروع المحلي الجديد، يجب أن يكون
المجلد الممرّر إلى `devpod up` موجوداً؛ وإلا قد يُفسَّر كعنوان مستودع.
اختر IDE-only أثناء أول `up` تفاعلي؛ لا يستطيع `configure` حفظ هذا الاختيار قبل
أن ينشئ DevPod كتلة SSH. راجع [المثال المحلي](../docs/devpod-credentials.md#open-a-local-workspace).

تعطّل الأوضاع المحمية أيضاً البحث التلقائي عن المفاتيح الخاصة. تؤثر إعدادات السياق
في جميع مساحات العمل التابعة له.

## التوافق

| المكوّن | التوافق |
| --- | --- |
| نظام التشغيل | Linux |
| Python | 3.10 والأحدث |
| Podman | Rootless 6.1.x |
| Compose provider | `podman-compose` 1.6.x عبر `podman compose` |
| DevPod | اختُبرت 0.6.15؛ وتُقبل النسخ الأخرى؛ أوامر Docker/Compose المدققة وقيود IDE موضحة أعلاه |
| Docker Compose v2 | غير مدعوم |

يرفض المثبّت سلسلة major/minor غير مدققة من Podman أو Compose. تعتمد الأغلفة
على سلوك provider CLI، لذلك تحتاج كل سلسلة جديدة إلى مراجعة واختبارات توافق.

لم يُتحقق بعد من توافق نسخ DevPod الأخرى. وتظل فحوص الوصول إلى بيانات الاعتماد
والأوامر المسموح بها سارية.

<a id="limitations"></a>

## القيود

- يتطلب فحص ignore استبعاد المسارات الحساسة في الجذر بالكامل. قد تتطلب استثناءات
  الملفات المتفرعة أو الأنماط غير المراجعة قاعدة استبعاد صريحة في النهاية.
  تتطلب سياقات الصور الإضافية بادئة نقل صريحة. راجع
  [قيود البناء](../docs/direct-policy.md#build-boundary).
- يمكن للوكيل التوقيع بهوية المشروع دون كشف المفتاح الخاص؛ ويجب أن يفرض خادم Git
  حدود الوصول إلى المستودع.
- الغلاف الموجود في `PATH` ليس sandbox. يمكن لعملية في المضيف تعمل بحسابك أن
  تستدعي Podman الحقيقي أو تصل مباشرة إلى الملفات نفسها.
- لا يستطيع الغلاف الحماية من ثغرات kernel أو Podman أو OCI runtime أو الصور أو
  parsers أو zero-day.
- شبكة الحاوية العادية ليست sandbox لحركة البيانات الصادرة.
- يمكن لعمليات build تنفيذ تعليمات صورة عشوائية وقراءة أي مسار context لا
  يستثنيه `.containerignore` أو `.dockerignore`. يفحص guard مسارات credentials
  الشائعة في الجذر والتعيينات الحرفية الواضحة فقط.
- لا تحصل الحاويات المنشأة سابقاً أو العاملة بالفعل على mount protections جديدة.
  ترفض أوامر lifecycle المحمية النشطة الحاويات التي لا تحمل provenance السياسة
  والتثبيت الحاليين.
- provenance labels مؤشرات توافق محلية وليست تواقيع تشفيرية. يمكن لعملية تعمل
  بالفعل بحساب مستخدم المضيف قراءتها أو نسخها أو تجاوزها. يستخدم تشغيل guards
  مباشرة من source tree من دون installation ID صريح قيمة تطوير حتمية؛ استخدم
  المثبّت للحصول على provenance خاصة بالتثبيت.
- يمكن أن تتغير الملفات بين التحقق وتشغيل المزوّد.
- الواجهة المدعومة أصغر عمداً من واجهتي Podman وCompose الكاملتين.

استخدم VM مؤقتة أو حساباً منفصلاً قليل الصلاحيات عند الحاجة إلى عزل أقوى.

<a id="development"></a>

## التطوير

فحوص محلية سريعة:

```bash
scripts/test.sh
scripts/check.sh syntax
```

تستخدم الاختبارات المحلية مزوّدات وهمية ومجلدات منزل وإعدادات مؤقتة، وتُعطّل خيارات التكامل الموروثة. يعمل `scripts/check.sh` افتراضياً بوضع `local`، مع Ruff, mypy وBandit وShellCheck و`zizmor` دون شبكة وفحص Gitleaks للمصدر مع حجب الأسرار. يشغّل `scripts/audit.sh dependencies` تدقيق الشبكة صراحةً؛ ويضيفه `scripts/check.sh all` دون تشغيل تكاملات حقيقية. يطبّق `scripts/format.sh` التنسيق. حضّر الأدوات بشكل منفصل وفق [CONTRIBUTING.md](../CONTRIBUTING.md). تفصل CI بين الاختبارات والفحوص الثابتة والأسرار وتدقيق الاعتماديات.

التنفيذ ضمن `src/paranoid_podman`. راجع [خريطة الكود](../docs/architecture.md) و[تعليمات بناء wheel وتثبيته دون اتصال](../docs/wheel-packaging.md).

| المجلد | الغرض |
| --- | --- |
| `src/paranoid_podman/` | كود التطبيق |
| `bin/` | مشغّلات صغيرة لتشغيل المصدر والاختبارات |
| `dist/` | ملف wheel وقيمة التحقق الناتجان عن البناء |

ينشئ المثبّت الأوامر في `--bindir` بصورة منفصلة لتعمل ضمن بيئة Python الخاصة.
يبقى `bin/` جزءاً من شجرة المصدر.

يختار `scripts/test.sh compose-provider` فحص إعادة التحليل بمزوّد Compose الحقيقي. قد يستعلم من Podman دون تشغيل حاويات؛ استخدم بيئة مؤقتة مع الإصدارات المدققة.
تختبر هذه المجموعة أيضاً الاستخدام اليومي عبر Compose الحقيقي ومحرك بديل يسجل
الاستدعاءات؛ وقد أضيفت إلى CI.

تحتاج مجموعة الاختبارات الاختيارية بحاويات حقيقية إلى صورة محلية موجودة تحتوي `sh` و`sleep`. لا
تسحب أي صورة أبداً، وتستخدم فقط حاويات مؤقتة ذات أسماء فريدة:

```bash
PARANOID_PODMAN_TEST_IMAGE=docker.io/library/alpine:latest \
  scripts/test.sh rootless
```

شغّلها فقط مع إصدارات Podman وCompose المدققة، ضمن حساب rootless مؤقت لا يحتوي
حاويات أو credentials مهمة.

ينشئ اختبار وكيل SSH مفتاحاً ومقبساً مؤقتين، ولا يقرأ مفاتيح SSH المعتادة:

```bash
scripts/test.sh ssh-agent
```
